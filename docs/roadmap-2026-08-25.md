# Image-Search Professionalization Roadmap

**Date:** 2026-08-25
**Status:** Discussion
**Author:** Isaac + Hermes

---

## Context

Image-search is a self-hosted semantic image search app. The search engine (SigLIP2 embeddings → Qdrant → text/image queries with pos/neg prompts, diversity re-ranking, centroid blending, For You feed) is genuinely strong — more sophisticated than PhotoPrism's search.

What's missing is the library management and operational layer that mature photo apps treat as table stakes: EXIF display, timeline navigation, map view, auto-import, thumbnail pipeline, batch operations, responsive design, dashboard. These aren't fancy — they're what makes a photo app feel like a photo app instead of a search demo.

This document captures the architectural and operational debts that need to be addressed before new product features are added.

---

## Tasks

### 1. User-selectable SigLIP2 model

Currently hardcoded to `ViT-gopt-16-SigLIP2-384` (1536-dim, ~9GB). This is the largest variant — great quality but slow on CPU and enormous on disk.

**What needs to happen:**
- Allow the user to choose which SigLIP2 variant to use (e.g., `ViT-B-16-SigLIP2-256` at 768-dim as a sensible default).
- The model choice must be persisted and detectable on startup so the app knows whether it matches the indexed data.
- Changing the model means the embedding dimension changes, which invalidates the existing Qdrant collection. The user must be informed and given a path to re-index.
- Qdrant collection naming should incorporate the dimension so old and new collections can coexist during migration.

**Open questions:**
- Should there be a UI model picker (settings page), or is an env var / CLI flag sufficient for now?
- What's the re-index UX for a large library (100K+ photos)? Progress bar? Background job? Downtime warning?

---

### 2. Lazy-load model instead of baking into container

The Docker image currently pre-downloads the SigLIP2 model at build time, resulting in a ~9.5GB image. This makes pulls slow, storage expensive, and model swaps require a full rebuild.

**What needs to happen:**
- Remove the model from the Docker image build.
- Download the model on first boot (or first search request) and cache it to a persistent volume.
- Surface loading state to the user — first request takes 30-60s while the model warms up, and the UI should show progress rather than appearing broken.
- The indexer should follow the same pattern (lazy load, cache to volume).

**Open questions:**
- Download on container start (blocking, with progress logs) vs. download on first request (non-blocking startup, slow first query)?
- Should there be a pre-warm endpoint or health check that gates readiness until the model is loaded?

---

### 3. Qdrant as built-in sidecar

Qdrant setup is currently entirely the user's responsibility. The docker-compose includes it for dev, but there's no production compose, no one-command deployment, and no guidance beyond "run Qdrant yourself."

**What needs to happen:**
- Provide a production-ready docker-compose that bundles Qdrant as a sidecar service alongside the search container.
- Qdrant gets a named volume for persistent data, a health check, and auto-restart.
- `QDRANT_URL` defaults to the sidecar so zero-config works out of the box.
- One `docker compose up` should bring up the entire stack (Qdrant + search API + SPA) with no manual steps.

**Open questions:**
- Should the sidecar be the only supported deployment mode, or should standalone Qdrant (for users who already run it) remain supported?
- Is there a path to Qdrant embedded mode for single-binary deployments, or is that over-engineering?

---

### 4. Reconcile image-search (web) and image-search-desktop

Both apps exist. The web app uses Python + Qdrant + open_clip_torch. The desktop app uses Node.js + HNSW + SQLite + onnxruntime-node + Electron. They share a kernel (`image_search_kernel/`) but diverge significantly at the storage and runtime layers.

**What needs to happen:**
- Maximize what's shared: the embedding pipeline contract, the search API contract (OpenAPI spec), and the frontend components (both are Svelte).
- Accept what will never be shared: storage layer (Qdrant vs HNSW+SQLite), runtime (Python vs Node.js), deployment (Docker vs Electron).
- Formalize the shared kernel as a first-class package or git submodule that both repos reference.
- Define a `SearchProvider` interface so each app can implement search against its own backend while sharing the query/result contract.

**Open questions:**
- Should the frontend components be a published package, a git subtree, or just manually synced?
- How much of the search UI (SearchComposer, SearchGrid, Lightbox) can be shared given the different data sources?
- Is the desktop app's ONNX SigLIP2 path worth bringing back to the web app for the smaller model variants?

---

### 5. Thorough E2E testing with real data

Current test coverage is unit-level (27 frontend tests, ~50 backend test files). The Playwright config exists but is broken (empty `webServer.command`). There are no integration tests against a real photo library.

**What needs to happen:**
- A fixture set of 100+ real images with variety (different cameras, dates, GPS, people, scenes, formats). Committed to a test data repo or directory.
- A test setup that indexes the fixtures into a known Qdrant collection + SQLite baseline.
- Playwright E2E tests against the full stack (Qdrant + backend + frontend).
- Test categories: smoke (app loads, search works, lightbox opens), core flows (search, albums, favorites, for-you), edge cases (empty results, rapid interaction, concurrent searches).
- CI integration that runs the full stack and the Playwright suite.

**Open questions:**
- Where does the fixture set live? Separate repo (keeps main repo lean) vs. committed directory (simpler CI)?
- Should the test Qdrant collection be committed as a snapshot, or regenerated each CI run?
- How much non-determinism is acceptable in semantic search tests? (Test that results are *reasonable*, not exact ordering.)
- Visual regression screenshots — worth the flakiness, or skip?

---

## Sequencing (recommended, not committed)

Items 3 (Qdrant sidecar) and 2 (lazy model) are the foundation — everything else is easier when deployment is simple.

Item 1 (model picker) depends on #2 being done first (no point letting users pick a model if it's still baked into the image).

Item 5 (E2E testing) is the safety net that lets items 1 and 4 proceed without fear of breaking things. Should be started early and grown incrementally.

Item 4 (desktop reconciliation) is ongoing background work, not a rush.

```
Phase 1: Qdrant sidecar + lazy model loading → one-command deployment
Phase 2: Model picker → default to smaller variant, env var / CLI override
Phase 3: E2E testing → fixture set + Playwright + CI
Phase 4: Desktop reconciliation → shared kernel + frontend components
```
